## 今日の追記: プロフィール保存の不正リクエスト修正

- 表示名の保存時に「不正なリクエストです。」と表示される原因を調査した。
- `/api/profile`が`request.nextUrl.origin`だけを比較していたため、開発サーバー内部の`localhost`とブラウザーの`127.0.0.1`が異なる環境で、正当な同一オリジン操作まで403になっていた。
- `lib/request-security.ts`に、転送先またはHostヘッダーから実際の公開先を組み立ててOriginと比較する共通検証を追加した。
- プロフィール保存だけでなく、レビュー投稿といいねの状態変更にも同じ検証を適用し、同じ開発環境差異による不具合を防いだ。

### 検証

- `npm run typecheck` 成功
- `npm run lint` 成功
- `git diff --check` 成功
- `Host: 127.0.0.1:3008` と`Origin: http://127.0.0.1:3008`の保存リクエストが403ではなく401（認証確認）まで進むことを確認した。
- `Host`と`Origin`が異なる組み合わせ、外部Origin、Originなしは403のまま拒否されることを確認した。

### 残る確認

- 認証済みブラウザーで実際にSupabaseへ表示名が保存されるところは、ユーザーのセッションをこちらで再現できないため未確認。
- サーバーログにはWorkOS JWTの発行時刻がSupabase側より未来として扱われた記録があるため、403解消後に保存が500になる場合は端末時計・WorkOS/Supabaseの時刻同期を追加確認する。

### 実装レビューと追加修正

- 独立したコードレビューを実施し、WorkOS以外のSupabase JWTでもRLSの書き込み条件を満たし得る問題を確認した。
- `is_workos_authenticated()`を追加し、WorkOSのissuer形式と`role`を確認したうえで、`sub`と所有者IDを照合するRLSへ更新した。

- アバターをユーザーごとに一つの固定Storageパスへ保存し、更新のたびに未参照ファイルが残らないようにした。公開URLにはキャッシュ更新用のバージョン値だけを付与する。
- 画像読み込み中は保存ボタンを無効化し、連続選択した場合に古い`FileReader`の結果が復活しないようにした。
- Data URLはデコード前の文字数確認と、3MB上限のストリーム読み込みを追加した。プロフィール編集だけでなくレビュー投稿にも同じ上限を適用した。
- ローカル確認モードで画像保存に失敗した場合は、表示名・紹介文・画像の保存前状態を復元するようにした。
- Supabase Advisorが指摘したRLS関数の可変`search_path`も追加migrationで固定した。

### 追加検証

- Supabaseのmigration反映成功
- SupabaseネイティブJWT形式では`is_workos_authenticated()`が`false`になることを確認した。
- WorkOS issuer形式のJWTでは同関数が`true`になることを確認した。
- Security AdvisorのRLS関数`search_path`警告が解消したことを確認した。
- 残るAdvisor警告はSupabase Authの漏えいパスワード保護が無効という設定で、現在のアプリ認証経路はWorkOSのメールコード方式であり、RLSではSupabase AuthのJWTを拒否する。

### 残る判断

- `profiles`は従来から投稿者名・アバターを匿名公開する設計で、今回追加した紹介文も同じテーブルにあるため匿名Data APIから取得可能。紹介文を非公開にする場合は、本人専用の設定テーブルへ分離する設計変更が必要になる。公開プロフィールとして扱うかはプロダクト方針の確認が必要。
