## カタログ限定レビュー運用

### 実施したこと

- 公開前の仮運用では、運営が管理する仮の商品20品目だけをレビュー対象にする方針へ変更した。
- 投稿フォームを自由入力からカタログ選択へ変更し、商品詳細からの投稿は対象商品を初期選択、中央の投稿導線は未選択から始めるようにした。
- localStorage、投稿API、Supabaseの`reviews.product_id`必須制約、DBトリガーの4層で、未登録飲料や対象外商品のレビューを保存できないようにした。
- DBに`products.is_reviewable`を追加し、投稿可否の判定をDBへ一本化した。現在は20商品だけが`true`である。
- DBトリガーでレビューの`product_name`を商品マスタの名称へ強制し、直接Data API経由で商品名だけを書き換えられないようにした。
- 商品追加リクエストのUI、ローカル保存、RLSポリシーを停止し、既存のリクエスト行を削除した。
- 仮レビューが公開時に実在商品の評価として残らないよう、公開切替専用の`supabase/release/public-launch.sql.template`を追加した。切替時は投稿停止中に仮レビュー・いいね・レビュー画像を削除し、新しいIDの実在20商品を登録する。
- `20260721000000_restrict_reviews_to_catalog.sql`をSupabaseプロジェクトへ適用した。既存の未登録レビュー、商品リクエストはともに0件で、削除対象の画像も0件だった。

### 検証結果

- `npm run typecheck`: 成功。
- `npm run lint`: 成功。
- `npm test`: 5件成功。
- `npm run build -- --webpack`: 成功。
- `git diff --check`: 成功。
- Supabase実DB: レビュー0件、未登録レビュー0件、レビュー可能商品20件、`reviews.product_id`は`NOT NULL`、商品リクエストのRLSポリシー0件を確認した。
- ロールバックするDBトランザクションで、商品名のマスタ値への正規化と`is_reviewable=false`商品の投稿拒否を確認した。
- 実装レビューを行い、公開時の仮レビュー混入、投稿判定の二重管理、商品名改ざん、画像の孤立に関する指摘を反映した。再レビューでブロッカーなしを確認した。

### 判断と次回確認

- Supabaseは`storage.objects`へのSQL直接削除を保護しているため、レビュー画像の削除はStorage APIまたはStorage管理画面で実行する。通常投稿のINSERT失敗時は、APIが直前にアップロードした画像を削除する。
- 公開切替テンプレートは自動マイグレーションではない。実在商品名・メーカー・画像の利用許諾を確認し、投稿停止中に運営が実行する。
- Supabase Security Advisorの`product_requests`にRLSポリシーがないという情報通知は、機能を意図的に停止している状態を示す。パスワード流出保護の警告は、認証をWorkOSのメールコード方式へ委譲しているため、公開前に認証方式を変更しない限り適用対象外として扱う。

## ホーム画面用ダミーレビュー

### 実施したこと

- 今週のランキングと最新レビューを確認できるよう、仮カタログの商品へ6件のダミーレビューを追加した。
- 各レビューへ専用の仮プロフィール、評価、購入場所、シーン、コメント、異なる投稿時刻を設定し、5商品にレビューを用意した。ホームのランキングは上位4商品、新着欄は6件を表示する。
- ホーム画面の新着レビュー表示件数を2件から6件へ拡張した。
- 公開切替テンプレートへ、ダミーレビュー専用プロフィールの削除を追加した。

### 検証と判断

- Supabase実DBで6件のダミーレビューが保存され、商品名が商品マスタの名称へ正規化されることを確認した。
- ダミーデータは固定IDと固定投稿時刻を使うため、同じseedを再適用してもレビューが増殖・再新着化しない。
- 公開時は仮レビューと仮プロフィールを削除し、実在商品の評価として引き継がない。
- レビュー取得で`reviews`と`profiles`の結合先が曖昧になっていたため、`reviews.user_id`の外部キーを明示するよう修正した。iPhone幅で、ランキング4商品と最新レビュー6件が表示されることを確認した。
- 実装レビューで指摘された公開DBへのダミー混入を防ぐため、ダミーINSERTは通常マイグレーションから`supabase/seeds`へ分離した。現行の確認環境には6件が投入済みであり、公開時は既存の切替テンプレートで削除する。
- `npm run typecheck`、`npm run lint`、`npm test`、`npm run build -- --webpack`、`git diff --check`はすべて成功した。seedはロールバックするDBトランザクション内で再実行し、SQLエラーなく冪等に処理できることを確認した。
- 最終実装レビューではP1〜P3の指摘はなく、ダミーの公開混入防止・再実行時の時刻維持・`reviews`から`profiles`への結合指定を確認した。

## 週次ランキングの評価基準

### 実施したこと

- ホームの「今週のランキング」を直近7日間のレビューだけで集計するよう変更した。
- 補正済み平均評価を50%、レビュー1件あたりのいいねを20%、評価の信頼度を30%として順位を計算するようにした。信頼度は3件で上限となり、投稿数が多いだけでは有利にならない。
- 評価が1件だけの商品を週次全体の平均へ3件分寄せ、偶然の5.0評価だけで上位になりにくくした。
- 検索の人気順とマイページの人気商品は、週次ランキングへ意図せず変わらないよう既存の全期間ロジックを維持した。
- 週次の対象期間、いいねによる順位、少数高評価の補正を確認する回帰テストを追加した。
- Supabaseへ保存されたいいねは、成功後にレビュー一覧を同期してホームの週次順位へすぐ反映するようにした。

### 検証結果

- `npm run typecheck`、`npm run lint`、`npm test`（11件）、`npm run build -- --webpack`、`git diff --check`: すべて成功。
- iPhone幅のホームで、週次ランキング4商品と最新レビュー6件が表示され、ブラウザエラーがないことを確認した。
- 同点時は商品名、さらに同名なら不変のIDで順位を固定し、商品取得順に依存しないようにした。
- 最終実装レビューで、少数評価の信頼度・再取得時の表示維持・週次一覧への遷移・同名商品の同点処理を確認し、P1〜P3のブロッカーなしと判断された。
